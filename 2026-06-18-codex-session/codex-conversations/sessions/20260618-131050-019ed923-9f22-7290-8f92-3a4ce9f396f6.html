**Findings**

1. 当前 WorkOffset 集成属于 **NRT 内部 domain module + HMI server facade/adapter** 模式，不是 RT 通信模式。`nrt/work_offset` owns 真值、snapshot、axis/profile、active state、PersistenceStore 和 accepted write semantics；HMI owns `wcs.offset.table` resource facade、`wcs.commands.*` command facade、UI 状态、mock backend 和 server adapter。见 [architecture.md](/home/iaar/workspace/ccmix-wp/MetaNC/docs/dev/architecture.md:250):250-273、[work_offset README](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/work_offset/README.md:20):20-32、[contract.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/hmi/docs/project/work_offset/contract.md:22):22-29、[delivery_plan.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/hmi/docs/project/work_offset/delivery_plan.md:51):51-54。

2. 实现边界是：HMI 公共侧依赖 C++17 `WorkOffsetBackend` facade；real backend 通过私有 C++20 bridge 链接 `work_offset::work_offset`，再调用 `StoreBackedWorkOffsetRuntime` over `PersistenceStore/SQLite`。这是一种 **同进程私有链接 + typed API adapter**，不是网络服务、不是 direct DB、不是 RT SDK。见 [CMakeLists.txt](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/hmi/server/CMakeLists.txt:111):111-157、[work_offset_backend.h](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/hmi/server/include/hmi/extensions/work_offset/work_offset_backend.h:72):72-88、[real_work_offset_backend_factory.cpp](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/hmi/server/src/extensions/work_offset/real_work_offset_backend_factory.cpp:99):99-113、[work_offset_backend_adapter.cpp](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/hmi/server/src/extensions/work_offset/work_offset_backend_adapter.cpp:384):384-527。

3. 这个模式适合 NRT 管理/配置/投影类模块之间复用：Tooling Management、WorkOffset、参数表、日志/诊断资源、部分 program workspace。共同特征是：HMI 需要资源投影和显式命令，domain module 保持真值和校验，mock/real backend 可并存，revision guard 可处理本地并发。它不适合作为 NRT->RT、RT SDK、RT API Contract 的组织/通信模式；这些边界已被 architecture 约束为 scheduler -> `/rt-sdk` -> backend protocol -> RT runtime，且 `/rt-api-contract` 是 RT 与 SDK 间唯一共享 contract package。见 [architecture.md](/home/iaar/workspace/ccmix-wp/MetaNC/docs/dev/architecture.md:131):131-179、[architecture.md](/home/iaar/workspace/ccmix-wp/MetaNC/docs/dev/architecture.md:202):202-212、[architecture.md](/home/iaar/workspace/ccmix-wp/MetaNC/docs/dev/architecture.md:224):224-226。

**讨论框架**

建议按 5 个维度讨论全模块组织：truth owner、timing/safety class、通信拓扑、状态一致性/持久化、部署/构建边界。

候选方案：
1. **NRT domain library + HMI facade**：当前 WorkOffset/Tooling 形态。适合管理数据、operator workflow、local persistence、mock/real 并行。
2. **NRT service/event boundary**：domain 作为独立服务或明确进程边界，HMI/ProgramEngine 通过 typed request/event 交互。适合多进程、多写者、强审计和长期扩展，但成本更高。
3. **RT-bound SDK contract path**：NRT execution/scheduler 通过 RT SDK 和 RT API Contract 访问 RT runtime。适合 motion/PLC/HAL/telemetry，不允许复用 WorkOffset 的同进程私有 bridge 作为 RT 边界。
