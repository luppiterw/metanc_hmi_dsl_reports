我会按“只读盘点 → 分层确认 → 执行清理 → 压缩回收 → 验证”的顺序来做，不会一上来直接删。

**总体原则**
- 先分清三类空间：Windows C 盘原生文件、WSL Linux 文件、Docker/WSL 的 VHDX 虚拟磁盘占用。
- Docker 空间不能简单相加，要看 shared/unique/reclaimable；优先清 BuildKit cache，而不是直接 `docker system prune -a`。
- WSL 里删掉文件后，C 盘上的 `ext4.vhdx` 不一定马上变小；最后还要做 WSL 关闭后的 VHDX compact/稀疏化。
- 所有删除动作先列清单，按“可安全删 / 需确认 / 不动”三档处理。

**第 1 步：只读盘点**
- Windows 侧：查 C 盘根目录、`Users`、`AppData`、下载目录、Windows Update 缓存、临时文件、Docker Desktop/WSL VHDX 文件。
- WSL 侧：跑 `df -hT`、`du -xh -d1 ~`，重点看 `workspace`、`~/.cache`、`~/.npm`、`~/.codex`、`~/.vscode-server`、`~/.local`、`~/.rustup`、`~/.nvm`。
- Docker 侧：跑 `docker system df -v`、`docker builder du --verbose`、`docker ps -a`、`docker volume ls`，分清镜像、容器、volume、build cache。

**第 2 步：优先清低风险项**
- Windows：回收站、临时文件、Windows Update 清理、Delivery Optimization 缓存、旧安装包、浏览器/工具缓存。
- WSL：`/tmp` 中确认无用的临时目录、旧 build 输出、明显可再生成的项目产物、过期包缓存。
- Docker：优先 `docker builder prune` 清 BuildKit cache；这个通常比删镜像安全，因为不会直接移除当前 tagged runtime images。

**第 3 步：谨慎处理开发环境大户**
- Docker 镜像：保留当前还会被脚本引用的 runtime/base 镜像；比如 MetaNC 相关镜像要先按角色判断，不能因为“没运行容器”就删。
- `workspace`：只清已确认废弃的 build 目录、临时 worktree、旧归档；不碰有未提交改动的 repo。
- `~/.codex`、`~/.vscode-server`、`~/.rustup`、`~/.nvm`：不整目录删除，只按旧版本、旧缓存、可重装内容裁剪。
- `.git`：先看 `git status` 和 pack/tmp_pack，再考虑 `git gc`，不直接手删对象库。

**第 4 步：回收 C 盘上的 WSL 空间**
- 清完 WSL 内部文件后，从 Windows 执行 `wsl --shutdown`。
- 再按当前 Windows/WSL 版本选择 VHDX compact 或 sparse 方案。
- 这一步很关键：否则 Linux 里 `df` 变小了，但 C 盘看到的 VHDX 可能还保持膨胀。

**第 5 步：验收**
- 对比清理前后：C 盘剩余空间、WSL `df -h`、Docker `system df`。
- 启动一次常用 WSL、Docker、MetaNC/开发流程，确认没有删掉关键 runtime。
- 最后输出一份“删了什么、释放多少、哪些没动、后续可选项”的记录。

如果我来实际执行，第一轮我只会做扫描和清单，不删除；等你确认哪些档位可以清，再分批执行。这样能避免把开发镜像、历史会话、未提交项目或 WSL 虚拟盘处理错。
