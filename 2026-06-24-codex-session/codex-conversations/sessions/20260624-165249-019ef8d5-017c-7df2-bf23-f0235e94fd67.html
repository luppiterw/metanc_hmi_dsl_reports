**为什么不先并列拆**
- `TOPICS.md` 明确说 `TPnnn-slug` 是稳定 topic package ID，不是术语、模块名或代码包名；把 `rt_gateway`、`execution_policy`、`data_diagnostics` 直接升成 TP，会把实现结构误固化成规范边界。
- 现有 `TP004-parameter-system` 已覆盖 `Runtime Access`，再建 `runtime access` topic 会立刻重叠。
- roadmap 里的 P1-P5 是推进顺序：P1 网关、P2 参数窄切片、P3 policy、P4 ProgramEngine 接入、P5 诊断/仿真；它们天然互相依赖，不是彼此独立的规范域。
- `execution_policy` 横跨 HMI、ProgramEngine、Parameter Service、RT Gateway；单独成 TP 会把“命令允许性判断”从端到端链路里抽走，导致每个 topic 都要引用它。
- `data diagnostics` 和 `simulation validation` 更像验收/观测层，应先作为每个 vertical slice 的 evidence 要求，而不是先拥有独立 topic。
- `program execution gateway integration` 是集成故事，不是领域边界；它依赖 ProgramEngine、RT Gateway、policy、diagnostics，先拆 topic 会制造大量跨 TP 同步成本。
- 当前 registry 的 placeholder promotion 要求同一 changeset 更新 registry、补 topic-local baseline、同步读者表；如果一次新增多个，还没有稳定 baseline，会制造维护债。

**最小替代方案**
- 先不改 `TOPICS.md`，新增/沉淀一份 **MetaNC Architecture Roadmap**，定位为跨 topic 路线图，不是新 TP。
- Roadmap 只维护三类内容：端到端依赖链、vertical slice 顺序、哪些概念暂不升 topic。
- 先做 2-3 个 vertical slice：
- Slice 1：`RT Gateway 最小闭环`
  只验证 Connect/Disconnect/Health/Topology/Mode/AutomaticStatus，目标是唯一 RT 通讯入口。
- Slice 2：`TP004 Runtime Access 窄切片`
  放在现有 TP004 内，先接 WorkOffset read、Tooling read、少量 owner-defined write，不做完整 840D catalog。
- Slice 3：`Program Execution Gateway Integration`
  ProgramEngine/Scheduler 通过 RT Gateway 走 MDI/AUTO 最小流；diagnostics 和 simulation 作为验收证据附着在该 slice 上。

**以后拆 topic 的触发条件**
- 至少两个 vertical slice 已经复用同一契约，且契约边界稳定。
- 能写出独立 `README.md` + `DESIGN-BASELINE.md`，并明确“不覆盖 TP001-TP005 哪些内容”。
- 有独立 owner、术语表、validation set，而不是只靠一个代码目录名。
- 跨 topic 引用数量低于 topic 内部定义数量；否则说明它还是横切层或集成故事。
- 拆出去后能减少维护成本，而不是增加同步矩阵。
- 有读者侧收益：单独成书/成章能让人更快理解，而不是为了目录整齐。

我的保守建议：**先用 architecture roadmap 管住全局，再用 3 个 vertical slice 验证边界；等边界被实现和验证“压实”后，再拆 topic。**
