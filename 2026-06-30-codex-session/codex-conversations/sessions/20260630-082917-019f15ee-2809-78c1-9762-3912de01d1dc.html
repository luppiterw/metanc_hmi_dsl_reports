`nrt/rt_gateway` is the NRT-side RT access boundary above `rt-sdk`.

The current MVP is an in-process gateway for one NRT runtime process and one
active RT endpoint session:

- start and stop a `GatewayOwner`;
- open, reject, or replace one active RT endpoint session;
- expose gateway health, last error, topology, mode, and SDK-backed runtime

# Documentation Guide

This is the authoritative reference for writing and organizing documentation in MetaNC.

## Philosophy

Source markdown is the primary artifact. Both humans and AI agents read `.md` files directly. The bookshelf build produces a rendered site for humans, but the source tree must be navigable and self-explanatory on its own.

This means:

- Directory and file names must be meaningful without consulting the owning book's `SUMMARY.md`.
- No page should be a pure redirect stub. If a page exists, it contains real content.
- Cross-references work as relative markdown links, not only as rendered HTML links.
- No empty placeholder pages. Structure follows content, not the other way around. Add pages to the owning book's `SUMMARY.md` when they have real content; remove them when they don't.

## Where Docs Live

Documentation lives at two levels:

- **Repo-level docs** live in `docs/`. These cover project-wide concerns: architecture, build toolchain, getting started, development practices, and domain chapters.
- **Module-level docs** live under `<module>/docs/`. Each module (as defined by the ARCHITECTURE.md Codemap) owns its own documentation.

Documentation builds as a bookshelf site from the repo root:

- `bookshelf.toml` is the site configuration.
- `docs/` is the root `MetaNC` book.
- configured module books own their own source roots and summaries.
- each book keeps its canonical reading order in `<book src>/SUMMARY.md`.

### Allowed repo-root and module-root files

`README.md`, `AGENTS.md`, and `CLAUDE.md` may live at the repo root or at a module root. These serve as entry points and agent instructions. All other documentation belongs inside the respective `docs/` directory.

## Path Conventions

All documentation links follow one of three conventions. The bookshelf site root equals the repo root, so site-root-relative pat<truncated omitted_approx_tokens="592" />ing document and code.

## Decision Records

When a documentation or design decision involves choosing between alternatives, rejecting approaches, or explaining rationale that readers would otherwise not understand, record it as a decision record.

Two storage formats:

- **Sidecar file** (`X.decisions.md`): use when there are only a few decisions. Keep under 1000 words.
- **Decision folder** (`X.decision/`): use when the sidecar would exceed 1000 words. Each decision gets its own numbered file.

See `.agents/skills/document-decision-records/SKILL.md` for the full entry template and workflow.

# RT Gateway Architecture

## Role

`rt_gateway` is the NRT-side owner of the RT SDK session. It gives HMI,
ProgramEngine, TP004 runtime access, diagnostics, and future NRT modules one
stable RT availability surface without letting each module create and manage
its own `rt-sdk::Machine`.

```text
NRT callers
  -> rt_gateway
    -> rt-sdk::Machine
      -> OPC UA + rt-api-contract payloads
        -> Orocos RtApi / RT runtime
```

## First Slice

The first slice is observability only:

- endpoint configuration for one active machine session;
- connect and disconnect;
- health and last-error reporting;
- topology and mode snapshots;
- SDK/backend error classification;
- fake-client tests and one live smoke harness.

Command forwarding, manual jog, automatic execution, MDA, reconnect watchdogs,
and ROS 2 public services are later slices.

## Internal Shape

```text
GatewayCore
  -> MachineClientFactory
    -> MachineClient

RtSdkMachineClientFactory
  -> RtSdkMachineClient
    -> rt-sdk::Machine
```

`GatewayCore` does not include `rt-sdk` or ROS 2 headers. It owns state
transitions and maps client results into stable gateway snapshots.

`RtSdkMachineClient` is the only first-slice adapter that includes
`meta_nc/rt_sdk/*`.

## Non-Responsibilities

`rt_gateway` does not own:

- ProgramEngine execution semantics;
- instruction scheduling policy;
- G-code parsing;
- TP004 descriptor or catalog rules;
- WorkOffset or Tooling domain semantics;
- diagnostics history retention;
- RT Core algorithms;
- Orocos activities or deployer scripts.

# RT Gateway Failure Model

## Gateway State

```text
not_configured
  -> disconnected
  -> connecting
  -> connected
  -> degraded
  -> failed
```

The first slice performs only explicit connect, disconnect, and refresh calls.
Automatic reconnect is deferred.

## Error Stages

The gateway reports stable NRT-facing stages:

- `none`
- `validate_config`
- `open_transport`
- `authenticate`
- `handshake`
- `initialize_session`
- `query_topology`
- `query_mode`
- `query_runtime_projection`
- `disconnect`
- `internal`

Connection stages map directly from `rt-sdk` when available. Query stages are
gateway-owned wrappers around SDK topology, mode, and runtime projection reads.

## Health

- `unavailable`: no usable RT connection exists.
- `connecting`: a connect attempt is in progress.
- `ready`: topology and mode snapshots are available.
- `degraded`: connected earlier, but a refresh/query failed.
- `failed`: the latest operation failed before a usable session was established.

Long-term diagnostics storage is outside this module.

# RT Gateway Smoke

The smoke executable is a narrow harness for the first slice. It is not a
production IPC path.

Expected flow:

```text
rt_gateway_smoke
  -> GatewayCore
    -> RtSdkMachineClient
      -> rt-sdk::Machine
        -> OPC UA endpoint
```

```bash
docker run --rm -d --name metanc-rt-gateway-test \

  --endpoint opc.tcp://localhost:4840
```
