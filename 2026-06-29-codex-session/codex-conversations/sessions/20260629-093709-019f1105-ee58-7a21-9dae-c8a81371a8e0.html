Two HMI servers embedding this code can each create their own `GatewayCore` and independent SDK session, producing split observations and conflicting lifecycle decisions.

2. **High: draft owner/facade/IPC direction addresses the right problem, but is explicitly unimplemented.**
   The spec already introduces a long-lived owner that may be daemon or embedded and is “the single long-lived authority”: [STORY.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-02-gateway-lifecycle-ownership/STORY.md:18). But implementation status marks all owner, projection, facade, and IPC slices as draft/not implemented: [IMPLEMENTATION-STATUS.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/IMPLEMENTATION-STATUS.md:8). So current code must not be treated as multi-caller authoritative yet.

3. **Medium: current snapshot shape cannot prove freshness or authority.**
   `GatewaySnapshot` has state, health, endpoint, last_error, topology, and mode only: [types.hpp](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/include/rt_gateway/types.hpp:103). That does not yet specify queueing limits, operation timeout after dispatch, stale response handling, cancellation, caller-visible deadline exceeded, or whether snapshot reads may return stale-but-marked data instead of blocking.

**Data Consistency Risks**

Old/current interpretation:
- Safe for one HMI server or one process embedding exactly one `GatewayCore`.
- Unsafe for multiple HMI servers/NRT processes because each process can create its own owner-like object and its own SDK session.
- No split-brain prevention across processes.
- No shared revision/epoch means callers cannot compare observations from different gateway instances.
- Events are absent in implementation; polling callers may see divergent state depending on refresh timing.
- Disconnect/reconnect in one embedded instance does not invalidate snapshots held by another.

New proposed interpretation:
- Direction is sufficient if “authoritative owner per machine” is made enforceable, not just conceptual.
- Snapshot fields listed by the user are the right minimum vocabulary for accuracy: `owner_epoch`, `session_id`, `revision`, `observed_at`, `source`, `current/stale/unavailable`, `last_known`.
- It still needs hard constraints for owner election/lease, embedded-mode prohibition in multi-process deployments, epoch changes on owner replacement, and IPC deadline semantics.
- Event streams can remain non-authoritative if every event carries enough revision/epoch/session metadata for callers to recover via snapshot.

**Minimum Spec Constraints Needed**

- Define `GatewayOwner` identity: one authoritative owner per `{machine_id, endpoint_identity}` or chosen machine key.
- Define deployment modes: embedded allowed only when the deployment contains exactly one gateway owner process; multi-HMI/multi-server deployments must use daemon/shared-owner mode.
- Define owner acquisition: lock/lease/registry mechanism, lease renewal, startup rejection on existing owner, and behavior after owner crash.
- Define split-brain rule: two owners for the same machine must be detectable; non-authoritative owners must fail closed and expose `gateway-owner-conflict`.
- Define epoch/session semantics: `owner_epoch` changes on owner replacement; `session_id` changes on RT SDK session replacement; `revision` is monotonic only within one `{owner_epoch, session_id}` scope unless otherwise specified.
- Define snapshot consistency: every snapshot includes freshness, source, observed time, availability, and last-known/current distinction.
- Define event contract: events are hints only; callers must treat snapshot read as authoritative; event loss/gaps are detectable by revision and recoverable by snapshot.
- Define fan-out: multiple callers receive same authoritative snapshot stream and cannot directly own `rt_sdk::Machine`.
- Define failover: old owner shutdown/crash, stale owner lease expiry, new owner epoch creation, and caller-visible transition.
- Define IPC timing: queue limit, acceptance deadline, operation deadline, cancellation, timeout response, and stale-response rejection.
- Define command-forwarding precondition: no control command forwarding until owner authority and snapshot consistency are implemented.

**Verdict**

The old design is acceptable only as the first-slice observability MVP for a single in-process owner. It cannot safely support multiple HMI servers or multiple NRT processes without inconsistent state and possible split brain.

The new interpretation is the correct design direction. The next design decision should be: **make `GatewayOwner` the explicit authority boundary and choose the deployment rule for multi-server setups: embedded single-owner only, daemon/shared-owner required for multi-process.** After that, settle the snapshot epoch/session/revision contract before implementing facade/IPC or event streams.
