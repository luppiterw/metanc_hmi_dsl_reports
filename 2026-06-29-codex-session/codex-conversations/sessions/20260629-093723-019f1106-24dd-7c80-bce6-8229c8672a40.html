**Findings**

1. **High: full adoption would front-load process/lifecycle complexity beyond the next slice.**
   Current code is still a small in-process observability core: `GatewayCore` owns one `MachineClient`, connect/disconnect, topology/mode refresh, and a plain `GatewaySnapshot` ([gateway_core.hpp](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/include/rt_gateway/gateway_core.hpp:10), [gateway_core.cpp](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/src/gateway_core.cpp:21)). Current module rules explicitly defer command forwarding and keep daemon/IPC/reconnect outside the MVP ([AGENTS.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/AGENTS.md:11), [IMPLEMENTATION-STATUS.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/IMPLEMENTATION-STATUS.md:18)). A full “semantic/authority/entry layers + embedded/daemon/registry modes” implementation now would likely create abstractions before there are real callers.

2. **Medium: the new model is not actually new in broad direction; it overlaps existing draft stories.**
   Story 02 already defines a long-lived gateway owner that may later be daemon or embedded and is the single authority for endpoint configuration and one active session ([STORY.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-02-gateway-lifecycle-ownership/STORY.md:16)). Story 04 already defines a facade hiding in-process vs remote deployment ([SLICE.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-04-nrt-integration-envelope/SLICE-01-client-facade-contract/SLICE.md:12)). So the risk is not the idea; the risk is implementing too much of it before Story 02 Slice 01 has proven useful.

3. **Medium: consistency metadata is the best near-term adoption point, but keep it minimal.**
   Story 03 already calls for revision/timestamp/stale/source metadata ([STORY.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-03-runtime-state-projection/STORY.md:17), [SLICE.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-03-runtime-state-projection/SLICE-01-state-cache-baseline/SLICE.md:12)). `owner_epoch`, `session_id`, and `last_known` are not in current implemented types, and adding all three at once would expand [types.hpp](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/include/rt_gateway/types.hpp:103), tests, smoke output, and future IPC contracts. I would document these as future identity semantics now, but implement only `revision + stale/availability + timestamp` when there is a concrete snapshot-cache slice.

4. **Low/Medium: highest implementation risk is ownership semantics, not data fields.**
   The hard parts are `GatewayOwner` lifecycle, thread/run-loop cancellation, reconnect deadlines, duplicate session handling, and eventually IPC/event loss behavior. Those map to Story 02/03/04 draft surfaces ([INTERFACE-REGISTRY.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/INTERFACE-REGISTRY.md:31)). Files/classes that would grow: `types.hpp`, `GatewayCore`, new owner/facade headers, `gateway_core_tests.cpp`, fake client tests, smoke output, and later CMake targets for owner executable or IPC carrier.

**Recommendation**

Adopt the new model **partially**.

Implement next:
- Story 02 Slice 01 only: a small `GatewayOwner` lifecycle skeleton around `GatewayCore`, still in-process, no daemon, no IPC, no registry.
- Preserve existing `MachineClientFactory` seam and keep `rt-sdk` ownership inside `RtSdkMachineClientFactory`.
- Add tests for owner startup rejection, startup success, and shutdown disconnect.

Document only now:
- Semantic/authority/entry vocabulary.
- One authoritative owner per machine as the future rule.
- Facade remains the caller-facing contract for embedded and daemon modes.
- `owner_epoch/session_id` as future identity metadata tied to owner/session lifecycle.

Defer:
- Daemon packaging, IPC envelope, registry/discovery.
- ROS2 public surface.
- Event stream/subscriptions.
- Reconnect/backoff.
- Multi-machine.
- Command forwarding.
- Full `owner_epoch/session_id/last_known` implementation until a caller or event/IPC slice needs it.

**Middle Ground**

Use a three-layer naming model in docs, but implement only one layer now:

- Semantic layer: `GatewaySnapshot`, normalized errors, topology/mode, future projection metadata.
- Authority layer: `GatewayOwner` skeleton, exactly one owned `GatewayCore` and active SDK client path.
- Entry layer: today just direct C++ calls/smoke; facade/IPC/daemon are later entry carriers.

That keeps future scalability visible without making the next slice pay for daemon/registry/IPC mechanics. Verdict: **partial adoption**. The new model is directionally correct, but full implementation now would be overengineering. The next implementation should stay bounded to an owner skeleton plus possibly spec cleanup.
