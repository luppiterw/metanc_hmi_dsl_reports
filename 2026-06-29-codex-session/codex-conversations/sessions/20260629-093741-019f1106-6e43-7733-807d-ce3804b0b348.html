**Verdict**

Adopt the new model partially. The useful part is the authority clarification: `GatewayOwner` is the per-machine lifecycle/session authority; facade and IPC are access/carrier shapes; projection metadata belongs to gateway snapshots. Do not introduce “semantic layer / authority layer / entry layer” as prominent new taxonomy. The existing docs already have better host terms: `Gateway owner lifecycle`, `runtime state projection`, `NRT client facade`, `local IPC envelope`, `capability/result envelope`.

**Findings**

1. High: `GatewayCore` currently reads like the owner, but Story 02 makes `GatewayOwner` the later lifecycle authority.
Location: [MODULE-MODEL.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/MODULE-MODEL.md:8) says `GatewayCore` owns session transitions and snapshots; [STORY-02](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-02-gateway-lifecycle-ownership/STORY.md:18) says the owner is the single long-lived authority.
Reader effect: once Story 02 exists, readers can’t tell whether `GatewayCore` or `GatewayOwner` is authoritative for session identity and replacement.
Fix: make Module Model distinguish current implemented core from future owner: `GatewayCore` owns in-memory transition logic; `GatewayOwner` owns long-lived lifecycle and active-session authority once Story 02 is adopted.

2. Medium: the local architecture page overstates “RT SDK session owner” and includes TP004 runtime access in the role list.
Location: [architecture.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/architecture.md:5).
Reader effect: “owner of the RT SDK session” can be read as the final authority today, while the spec root still marks lifecycle ownership as deferred. TP004 also makes the gateway sound like a parameter/runtime semantic owner.
Fix: rewrite as “NRT-side access boundary above RT SDK; first slice centralizes one explicit session inside `GatewayCore`; Story 02 introduces the long-lived `GatewayOwner`.”

3. Medium: the proposed “entry layer” would duplicate existing facade/envelope wording and risk making IPC look semantic.
Location: [STORY-04](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-04-nrt-integration-envelope/STORY.md:18), [SLICE-02 Local IPC](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-04-nrt-integration-envelope/SLICE-02-local-ipc-envelope/SLICE.md:36).
Reader effect: if “entry layer” is added beside facade and IPC, readers may ask whether facade, IPC, or entry owns the public contract.
Fix: keep `NRT client facade` as caller-facing contract and `local IPC envelope` as carrier. If “entry” is used at all, use it once as plain explanatory prose, not a layer name.

4. Low/medium: consistency metadata is already present but should be anchored to projection, not introduced as a broad cross-layer concept.
Location: [STORY-03](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-03-runtime-state-projection/STORY.md:17), [State Cache Baseline](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-03-runtime-state-projection/SLICE-01-state-cache-baseline/SLICE.md:12), [INTERFACE-REGISTRY.md](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/INTERFACE-REGISTRY.md:43).
Reader effect: “consistency metadata” as a new umbrella term may blur revision/timestamp/stale/source/availability, which are already concrete and readable.
Fix: say “projection metadata” and list the fields.
