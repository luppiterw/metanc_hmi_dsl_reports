**Slice 4 Recommendation**

Current gap: server/mock contract support is mostly present, but generated Web/QML client behavior still uses the legacy Work Offset shape. `parameter_wcs_table` already binds to `res://wcs.offset.table` and should keep the same layout. Do not broaden the PARAM Work Offset page.

**Behavior Specs To Land**

1. Active-row display:
   Web/QML data tables should visually mark Work Offset rows where `row.active === true`. This can reuse existing row styling concepts, but it must be driven from the row’s `active` field, not from `wcs.active` guessing.

2. Cell edit enablement:
   For `parameter_wcs_table`, an editable cell is command-enabled only when:
   `row.editable === true`, `row.component_axis_ids[field]` exists, and the submitted value is finite.
   Missing axis mapping should block the client command and show a local notice such as `Work offset axis is unavailable; refresh and retry`.

3. WorkOffset edit payload:
   Generated Web/QML inline edit should emit:

   ```json
   {
     "g_code": "G55",
     "target_ref": "g55",
     "field": "offset_x",
     "axis_id": "x",
     "value": 12.5,
     "expected_revision": 1
   }
   ```

   `target_ref` comes from `row.target_ref`; `axis_id` from `row.component_axis_ids[field]`; `expected_revision` from `row.revision`. Keep `g_code` as compatibility echo.

4. Activation payload:
   Fixed G54/G55 buttons may remain in the current layout, but generated action dispatch should enrich `wcs.commands.activate` with visible row metadata when a matching row exists:

   ```json
   {
     "g_code": "G55",
     "selector": "G55",
     "expected_revision": 1
   }
   ```

   `expected_revision` must be the row’s `active_state_revision`, not row `revision` and not `snapshot_revision`.

5. No optimistic local patch:
   Web/QML local/mock command handlers for `wcs.commands.set_offset` should not locally mutate rows when a server-backed command rejects. In strict server mode, the command response plus post-command resource poll is authoritative. In local mock mode, accepted commands may update rows, but stale/mismatch rejections must leave the old row unchanged.

6. Stale notices:
   Generalize the current Tool Offset-only notice handling. Treat these as refresh-and-retry WorkOffset stale codes:
   `work_offset.revision_mismatch`, `work_offset.active_revision_mismatch`, and, for the Python fixture path, `wcs_revision_mismatch`.
   Client notice should be WorkOffset-specific:
   `Work offset table changed; refresh and retry`
   Include `(current X, expected Y)` when details contain both revisions.
