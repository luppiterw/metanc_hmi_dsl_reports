下面按 **RT SDK command completion model** 规划。目标不是接 live runtime，而是先把“accepted 后怎么关联、怎么查询完成状态”的 C++ placeholder 合同定下来。

**目标**
新增一个最小 command completion placeholder：

- accepted power-service command 返回 `command_id`。
- `machine.commands().status(command_id)` 可以查询命令状态。
- 当前 placeholder 立即返回终态 `completed`，但不改变资源 state。
- rejected receipt 不分配 `command_id`。
- default/unknown command id 查询走正常 read failure。
- 不接 PLC、不跑 runtime、不做队列、不做异步执行。

**核心边界**
这片只解决“命令生命周期外壳”：

| 做 | 不做 |
|---|---|
| `CommandId` 分配 | 真实 runtime dispatch |
| `CommandCompletionStatus` / `CommandCompletion` DTO | command queue |
| `MachineCommandApi machine.commands()` | polling/subscription |
| accepted placeholder completion 查询 | 状态突变、servo_on 变 true |
| 测试 command id 和 completion shape | PLC bridge / transport |

**建议 API shape**
在 `rt-sdk/include/metanc/rt_sdk/command.hpp` 里扩展：

```cpp
enum class CommandCompletionStatus {
  accepted,
  running,
  completed,
  failed,
  canceled,
  timed_out,
  unknown,
};

enum class CommandCompletionErrorCode {
  service_unavailable,
  unknown_command,
};

struct CommandCompletion {
  CommandId command_id = 0;
  CommandCompletionStatus status = CommandCompletionStatus::unknown;
  std::optional<RejectionReason> failure_reason;
};

struct CommandCompletionError {
  CommandCompletionErrorCode code = CommandCompletionErrorCode::unknown_command;
  std::string message;
  bool retryable = false;
};

using CommandCompletionResult = ReadResult<CommandCompletion>;
```

这里我倾向复用现有 `ReadResult<T>` 结构，避免再造一个 result envelope。需要让 `command.hpp` include `parameters.hpp` 或把 common read result 拆出去；为了小改动，先 include `parameters.hpp` 可以接受。

新增 `MachineCommandApi`：

```cpp
class MachineCommandApi {
 public:
  MachineCommandApi() = default;
  explicit MachineCommandApi(bool service_available);

  [[nodiscard]] CommandCompletionResult status(CommandId command_id) const;

 private:
  bool service_available_ = false;
};
```

在 `Machine` 上新增：

```cpp
[[nodiscard]] MachineCommandApi commands() const;
```

**placeholder 语义**
当前 sim profile 行为：

- accepted power command：
  - `receipt.status = accepted`
  - `receipt.command_id = next id`
  - `receipt.reason = nullopt`
- rejected power command：
  - 不给 `command_id`
- `machine.commands().status(id)`：
  - valid machine 且 `id > 0`：返回 `completed`
  - default machine：`service_unavailable`
  - `id == 0`：`unknown_command`
- accepted command 不改变：
  - resource state
  - diagnostics
  - logs
  - parameters
  - topology
  - wait helper result

我刚复核到的现状：

- `rt-sdk` 的 `sim` backend 现在只做 backend-private `profile:<name>`，打开 `InMemorySimulationChannel`，返回静态 topology。
- `/rt/plc` 已有 `LocalRuntimeAdapter`，只暴露 `boot()` / `shutdown()` / `execute(RuntimeCommand)`，底下是 `RuntimeSimulationSession` 和 `CommandExecutor`。
- 当前文档明确要求：`/rt-sdk` 不能直接 link `/rt/plc`，也不能把 `RuntimeCommand` / `CommandResult` 变成 public SDK API。

**建议路线：A，先做设计 gate**
新增一页 RT SDK design doc，定义 live adapter 的私有边界：

- endpoint 稳定性分层：`profile:<name>` 继续 backend-private，不急着公开稳定 URI。
- adapter ownership：live runtime state source 归 backend-private adapter，不归 public `Machine` API。
- SDK/PLC 映射：PLC `LocalRuntimeAdapter` 只能作为证据和未来私有桥接目标，不能泄漏到 public headers。
- first implementation slice：先做内部 adapter interface + fake/live-ready contract tests，不直接接真实 PLC。
- blocked 项：public endpoint grammar、wire protocol、live state mutation、command-driven state transition。

**不建议路线**
- 直接在 `rt-sdk` 里 include/link `/rt/plc`：会破坏当前边界。
- 先定 public endpoint grammar：现在还早，容易把测试用 `profile:<name>` 误变成正式协议。
- 直接把 `RuntimeCommand` 映射成 SDK command model：会让 PLC-local command vocabulary 泄漏到 SDK。
