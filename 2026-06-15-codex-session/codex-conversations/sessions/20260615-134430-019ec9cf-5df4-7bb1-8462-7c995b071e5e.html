   **High: WorkOffset backend-unavailable handling can leave stale/seeded offset tables visible.**
   `WorkOffsetRuntimeExtensionAdapter::bootstrap_resources()` catches backend query exceptions and returns only `wcs.offset.table.diagnostic`, not `wcs.offset.table`. But `ServerApp::initialize()` merges adapter resources over `contract_.seed_resources`, and `refresh_from_adapter()` merges polled resources over the existing snapshot. Because absence never deletes a resource, an unavailable WorkOffset backend still leaves the seed table, or the last successful table, in `wcs.offset.table`; `sync_wcs_offset_resource_aliases()` then mirrors that stale canonical value into `tooling.wcs.table`. That defeats the adapter’s “do not publish a successful table on unavailable backend” behavior and can present operator-visible WorkOffset data as current when the backend has failed. The unavailable path needs an explicit stale-table policy, such as publishing an empty/error table payload, tombstoning/removing the table, or failing startup for authoritative backends.
