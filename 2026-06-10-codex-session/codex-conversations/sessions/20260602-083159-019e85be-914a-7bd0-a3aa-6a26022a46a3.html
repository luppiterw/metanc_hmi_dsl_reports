Access Map 的基准应该是 **真实所有权**，不是表达式长得像什么。

平实说，要判断“谁跟谁绑定”，按这几个问题往下追：

1. **这个值真正存在哪里？**
   比如刀具半径、刀具长度、刀沿数据存在 tooling management 的刀具模型里，那就绑定 `tool_management`。

2. **谁负责修改它时的业务规则？**
   如果写入时要检查刀具号、刀沿号、刀具类型、磨耗、持久化，那 owner 就是能做这些校验的模块，不是参数系统。

3. **谁负责它的生命周期？**
   创建、删除、导入、导出、保存、重载、失效，这些归哪个模块，Access Map 就绑定哪个模块。

4. **谁能提供稳定 API？**
   TP004 不能直接改别人的内部数据结构，只能 dispatch 到 owner 提供的 read/write/resolve API。

5. **访问表达式只是入口，不决定 owner。**
   `$TC_DP3[10,1]` 看起来是 Siemens 参数，但语义上是“工具 10 的第 1 个刀沿的某个字段”，所以绑定 tooling management。
   `$MA_MAX_AX_VELO[X]` 看起来也是参数，但语义上是“X 轴最大速度配置”，所以绑定 motion/axis。

可以理解成这条链：

```text
外部表达式
  -> 语法解析
  -> 语义识别
  -> 找到真实对象类型
  -> 找到 owner 模块
  -> dispatch 到 owner API
```

例如：

```text
$TC_DP3[10,1]
  -> Siemens tool data expression
  -> tool=edge field
  -> object: tool 10 / edge 1 / field DP3
  -> owner: tool_management
  -> dispatch: read/write tool edge field
```

Access Map 的建立基准就是这几个绑定关系：

| 绑定项 | 判断基准 |
|---|---|
| expression -> semantic object | 表达式解析后代表什么真实对象 |
| semantic object -> owner | 谁拥有这个对象的数据和规则 |
| owner -> TP/module | 这个 owner 在哪个 TP 或代码模块里定义 |
| access kind -> schema kind | 它是 parameter、domain table field、signal、runtime state 还是 symbol |
| owner -> dispatch target | owner 暴露哪个 API 执行读写 |
| row -> evidence | 哪些文档/代码/测试证明这个绑定不是臆造 |

所以 Access Map 不能只写：

```text
$TC_DP3 -> tool_management
```

而应该写：

```text
$TC_DP3[tool,edge]
  kind: domain_table_field
  semantic object: tool cutting-edge field
  owner: tool_management
  owner evidence: TP002 tooling baseline / nrt/tooling_management
  dispatch target: TBD / needs alignment with real TP002 API
```

最重要的维护原则是：**绑定必须有证据，没有证据就标 conceptual/TBD，不能写成 confirmed。**

这样以后不会出现“AI 自创 owner、自创 API、自创参数语义”的问题。
Access Map 的价值就在于把“这个访问为什么归这个模块”写清楚，并且让后续实现、文档、schema 都能回查。
