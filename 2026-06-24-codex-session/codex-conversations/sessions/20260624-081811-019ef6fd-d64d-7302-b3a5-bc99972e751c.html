# RT SDK

The RT SDK is the userland interface for connecting to a realtime control
application and observing and commanding the machine-control surface it exposes.

## What You Connect To

- One SDK connection targets one RT application endpoint.
- In v1, that RT application exposes one machine-control surface, represented by
  `Machine`.
- `Machine` is the user-facing CNC operation handle: topology, resources, modes,
  manual / automatic / MDA control, parameters, and status.

> [!NOTE]
> `Machine` is the machine-control surface, not the RT endpoint itself. In a
> future version one RT application may expose multiple machine-control
> surfaces; a higher-level object (for example `RtApplication` or `Controller`
> with `application.machine(id)`) would be added then. The v1 model is one
> connection → one RT application → one `Machine`.

handles transport to the RT application.

# OPC UA Backend

## Component Roles

- `opcua` global service starts and stops the OPC UA server.
- `opcua_bind` component-local service exposes reviewed RTT services.
- `meta_nc_opcua_type_transport` is the RTT transport plugin.
- `meta_nc_opcua_type_protocol` owns protocol factories and OPC UA datatype
  providers.

Do not mix these roles.

## Resource Mapping

Generated/debug OPC UA nodes follow:

```text
Objects/components/<component>/services/<service_path>/
  operations/<operation>
  properties/<property>
  attributes/<attribute>
  ports/<port>/
    value
    active
    sequence
```

String NodeIds use the same path:

```text
ns=1;s=components/<component>/services/<service_path>/operations/<operation>
```

## Service Exposure

Use service-first exposure:

```ops
component.opcua_bind.exposeService("service")
```

Do not expose a raw internal component as the public SDK API just because the
binder can traverse it. Production SDK-facing surfaces should be curated behind
reviewed `RtApi` services.

## Values

- Properties map to read/write variables when the RTT datasource is assignable.
- Attributes map to read-only live variables.
- Output ports become browseable port objects through `exposeService()`.
- Output port live values require `startPortMonitor("service/port")`.
- OPC UA clients still use normal reads/subscriptions on generated variable
  nodes.

## Operations

OPC UA method binding should use RTT operation metadata:

```text
OperationInterfacePart
  -> arity()
  -> getArgumentType(1..arity)
  -> getArgumentType(0) for result
  -> getArgumentList()
  -> OpcUaTypeProtocol converts arguments/results
```

Do not add new method support by hardcoding signatures like
`int_int_int`, `double_double_double`, or one custom struct case at a time.

Valid operation exposure requires:

- every input argument has an `OpcUaTypeProtocol`
- result is `void` or has an `OpcUaTypeProtocol`
- TaskBrowser does not show `unknown_t`
- tests cover metadata and a real OPC UA client call

## Logging

Use `opcua.LibraryLogLevel = "error"` in deploy scripts unless investigating
server internals. Valid values are `off`, `fatal`, `error`, `warning`, `info`,
`debug`, and `trace`.

## `connect(config)`

Create one SDK `Machine` from connection configuration.

**Signature**

`connect(config)`

**Input**

| Field | Type | Meaning | Constraints |
|---|---|---|---|
| `backend` | `SdkBackend` | communication backend to use | supported SDK backend name; currently `OpcUa` |
| `endpoint` | `string` | backend-specific connection target | non-empty; interpreted by the selected SDK backend |
| `timeout` | `duration` | connection timeout | non-negative |

`SdkBackend` values:

| Backend | Transport | Endpoint Example |
|---|---|---|
| `OpcUa` | OPC UA | `opc.tcp://127.0.0.1:4840` |
| `sim` | reserved; not linked by the current SDK build | backend-defined |

**Return**

Return type: `ConnectResult`

| Field | Type | Meaning |
|---|---|---|
| `ok` | `bool` | whether connection succeeded |
| `machine` | `Machine?` | valid machine object when `ok=true` |
| `error` | `ConnectError?` | failure details when `ok=false` |

**Failure Result**

On normal connection failure:

- `ok = false`
- `machine` is absent and invalid
- `error` is present

`ConnectError` shape:

| Field | Type | Meaning |
|---|---|---|
| `code` | `ConnectErrorCode` | stable failure category |
| `message` | `string` | human-readable error message |
| `stage` | `ConnectStage` | stage where connect failed |
| `retryable` | `bool` | whether retry is reasonable |

`ConnectErrorCode` values for v1:

- `invalid_config`
- `endpoint_unreachable`
- `authentication_failed`
- `timeout`
- `protocol_error`
- `version_mismatch`
- `backend_unavailable`
- `transport_error`
- `internal_error`

`ConnectStage` values for v1:

- `validate_config`
- `open_transport`
- `authenticate`
- `handshake`
- `initialize_session`

**Exception**

Exceptions are not used for normal connection failure.

Exceptions are reserved for:

- SDK misuse that violates the API contract
- unrecoverable internal runtime failure
- language-binding or runtime failure outside the normal transport contract

**Interlock**

None in RT coordination terms.

**Effects**

Creates a valid `Machine` only when `ok=true`. The SDK owns the selected
backend instance after connection.

Backend constructors and test injection seams are not public user APIs. User
code starts from `Machine::connect(config)`.

The caller determines success from `ok`.

- if `ok=true`, `machine` is valid
- if `ok=false`, `error` describes the failure
