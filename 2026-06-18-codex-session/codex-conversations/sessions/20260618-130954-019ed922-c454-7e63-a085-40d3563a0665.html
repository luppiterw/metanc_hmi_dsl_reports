**Answers**

1. 是，同进程静态/库集成。证据是 `server_core` 通过 `add_subdirectory()` 拉入 `tooling_management`/`work_offset`，创建 `hmi_work_offset_real_backend STATIC`，再把它 link 到 `server_core`，运行时由 `make_default_work_offset_extension()` 直接构造 real backend，而不是通过 RT SDK、IPC 或服务边界调用。

2. 优点：类型边界直接、延迟低、便于本地测试，HMI 可以复用 WorkOffset 的真实语义和 SQLite store，不需要先设计跨进程协议。风险：构建和生命周期变成 HMI server 的一部分；C++20 模块会逐步压迫 C++17 server；ament/package 形态被绕开；SQLite/global env 成为隐藏配置面；任一 backend 启动失败会拖垮整个 HMI server；测试隔离必须靠 wrapper/env 临时 store 维持。

3. 代码级风险见上方 findings。当前最需要先收敛的是：把 real backend build 从运行时 launcher 中分离出来；把 WorkOffset store/seed 配置从全局 env 提升到显式 server config；给后续多模块定义“同进程库调用 vs 本地服务/RT SDK/IPC”的判定规则和失败隔离策略。只读审查，未改文件。
