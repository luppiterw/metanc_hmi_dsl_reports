P3 我建议按一个很窄的问题讨论：**Parameter Descriptor 要不要开始声明“这个参数的值长什么样”，但不声明“这个参数现在是什么值”。**

核心边界可以这样画：

```text
parameter_descriptor
  identity:
    parameter_id / owner / scope / semantic_name

  value metadata candidate:
    value.type
    value.unit_source

parameter_instance_binding
  instance keys:
    frame=G54 / axis=X / component=TR

runtime/configuration
  current value / storage / read-write / active profile lookup
```

**P3 要解决什么**
P3 不是补 runtime value，而是补 descriptor 的“值形态元数据”。也就是说，`zero_offset.frame_axis_component` 这个参数定义，可以声明它的值大体是 `float`，单位来源由 component 决定；`motion.axis.max_velocity` 可以声明值大体是 `float`，单位来源由 controller 决定。

这类信息对后续 UI、文档、校验、映射都有用，但它还不是读取值、写入值、默认值、当前值、持久化字段。

**当前可用资产**
仓库里已经有两套可以先评估复用的资产：

- `VS020020 / access_value_type`
  当前 token 有 `float`、`real`。问题是名字叫 `access_value_type`，历史上绑定在 `access_definition.value.type`，语义可能偏 access definition，不一定适合长期作为 descriptor value type。
- `VS040013 / unit_source`
  当前 token 有 `controller_defined`、`component_defined`、`controller/tool-type-defined`、`controller/profile-defined`。这套比较适合 P3，因为它不是具体工程单位，而是说明单位由谁定义。

**我倾向的 P3 第一版**
第一版只 formalize 两个可选字段：

```yaml
parameter_descriptor:
  parameter_id: zero_offset.frame_axis_component
  owner: zero_offset
  scope: frame_axis_component
  semantic_name: frame_axis_component
  value:
    type: float
    unit_source: component_defined
```

以及：

```yaml
parameter_descriptor:
  parameter_id: motion.axis.max_velocity
  owner: motion.axis
  scope: axis
  semantic_name: max_velocity
  value:
    type: float
    unit_source: controller_defined
```

注意这里用 `unit_source`，不要用 `unit`。`unit: mm`、`unit: degree`、`unit: mm/min` 这些会立刻碰到 component、axis type、controller profile 的差异，过早把 TP004 拉进完整单位系统。`unit_source` 只说“单位从哪里来”，边界更稳。

**不建议第一版做的内容**
第一版不应该加入：

- `current_value`
- `default_value`
- `min` / `max`
- `step`
- `precision`
- `readable` / `writable`
- `storage`
- `runtime_path`
- owner 自动校验捷径
- 真实单位枚举，如 `mm`、`deg`、`mm/min`

这些东西不是都没价值，而是会把 P3 拖成 runtime/value/constraint/access 混合设计。特别是 `min/max/default`，看起来像 descriptor 元数据，但实际经常依赖机型、轴、profile、通道状态或 controller，所以不该在 P3 第一版冻结。

**关键分歧**
P3 真正需要决定的是这个：

```text
方案 A：继续只记录边界，不 formalize 字段
方案 B：新增 parameter_descriptor.value.type + value.unit_source，并复用现有 value sets
方案 C：先拆出专用 parameter_value_type，再 formalize descriptor value
```

我的判断：**B 最合适**。
原因是现有证据已经够支持 `type` 和 `unit_source`，而且这两个字段不会触碰 runtime 行为。`access_value_type` 名字不完美，但第一版可以明确写成“临时复用现有候选 value set；如果后续名字/边界不合适，再单独拆 `parameter_value_type`”。不要为了命名洁癖先开一个新定义集。

**P3 的完成标准**
我认为 P3 formalization 做到这些就够了：

- `PARAMETER-DESCRIPTORS.md` 记录 `parameter_descriptor.value` 是可选 metadata block。
- `SCHEMA-FIELDS.md` 增加：
  - `parameter_descriptor.value.type -> VS020020 / access_value_type`
  - `parameter_descriptor.value.unit_source -> VS040013 / unit_source`
- checker 只校验 token 是否来自对应 value set。
- checker 继续禁止把它当 runtime value、默认值、存储值。
- 示例覆盖 `motion.axis.max_velocity` 和 `zero_offset.frame_axis_component`。
- 文档明确：P3 不处理 access，那是 P4；不处理 semantic path，那是 P5；不处理 runtime/API，那是 P7。

一句话：**P3 可以推进，但只推进“值形态元数据”这两格：`type` 和 `unit_source`。不要碰真实值、真实单位、约束、默认值、读写能力。**
