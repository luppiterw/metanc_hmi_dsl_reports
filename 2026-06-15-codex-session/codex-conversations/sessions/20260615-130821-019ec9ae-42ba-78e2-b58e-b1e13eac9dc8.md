**重构后的主链路**

8.30 目标应被压成一条纵向闭环，而不是多个并列“大系统”：

```text
固定 profile / 基础数据包
  -> HMI 或脚本启动入口
  -> ProgramEngine 创建 run/session，按 op01-op06 编排
  -> G-code parser ExecutionSession 解析并产出规范化命令
  -> TP004 access resolver + Tooling + WorkOffset 做运行时解析/前置检查
  -> RT SDK adapter 把命令转成 RT 可执行调用
  -> RT runtime / 仿真部署执行
  -> Telemetry/logs/report 采集并验证 run 证据
```

关键依赖顺序是：先冻结事实输入，再跑单工序，再串 6 道工序，最后长跑取证。不能反过来先做完整 TP005、完整参数宇宙或完整 HMI 平台。

**P0 必须闭环**

P0 只服务“固定机型、固定 6 道工序、可连续运行、可验证”：

| P0 项 | 必须闭环的结果 |
|---|---|
| 固定 profile | 轴组、主轴、通道、RT endpoint、IO/互锁占位、revision/hash |
| 基础数据包 | `machine_profile`、参数默认值、tooling seed、work_offset seed、6 道工序程序、telemetry schema |
| ProgramEngine MVP | 单 session，`start/pause/resume/cancel/status`，当前工序/程序/行块/失败原因 |
| G-code 子集 | 只覆盖 6 道工序实际用到的 G/M/变量/宏；形成覆盖矩阵 |
| RT SDK adapter | G0/G1、必要 G2/G3/G4、主轴/进给/等待、错误返回、必要 tool-change 占位 |
| Tooling/WorkOffset | 执行前 preflight、resolver、revision 进入报告；不承担执行器职责 |
| HMI/脚本入口 | HMI 观察和基本操作；脚本负责 smoke/soak/CI |
| Telemetry/report | `run_id/session_id/operation_id`、命令结果、RT 状态、参数/刀具/零偏快照、日志、24h 报告 |

**P1 可增强**

P1 是增强，不得阻塞 P0：

- HMI 更完整的参数/刀具/零偏页面、过滤、导出体验。
- TP004 更完整的 Parameter Descriptor、validation sets、owner 映射。
- RT/RT-SDK 更丰富的状态订阅、资源指标、断线诊断。
- PLC/IO 更真实的互锁模拟和状态采集。
- Tooling 的 sister tool、寿命策略、刀库拓扑细节。
- WorkOffset 的 rotation/scale/mirror 到运动矩阵的正式 ABI。
- 报告可视化、趋势分析、自动归档。

**明确不做**

- 不做完整 TP005 配置系统；8.30 用固定 profile/preset 替代。
- 不做完整 Siemens 840D 参数宇宙。
- 不做完整 PLC 语言前端、TIA import、Ladder/FBD。
- 不做任意 G-code 程序泛化。
- 不做生产级 session crash recovery。
- 不让 HMI 持有参数、刀具、零偏、PLC 的领域真相。
- 不让 Tooling 执行换刀，不让 WorkOffset 下发运动，不让 TP004 变成统一大数据库。

**模块责任边界**

| 模块 | 8.30 职责 | 明确边界 |
|---|---|---|
| TP004 | 参数与运行访问合同；定义最小 descriptor、owner、scope、读写/激活/持久化策略 | 不存领域真相，不把 domain table 打平成参数 |
| TP005 | 仅保留为后续配置系统主题 | P0 不启动完整配置系统 |
| TP003 | 最小 PLC/IO/互锁状态合同和采集项 | 不做 PLC 语言核心工程 |
| ProgramEngine | 主执行编排者；单 session；op01-op06 顺序、状态、事件、进度 | 不负责程序静态验证、历史存储、HMI 源文件生命周期 |
| G-code parser | `ExecutionSession`，解析目标子集并产出规范化 move/dwell/tool/diagnostic | 不直接连接 RT，不持有刀具/零偏真相 |
| RT/RT-SDK | userland 到 RT 的通信边界；执行运动/主轴/等待/模式命令并返回状态 | SDK 不链接 RT core；不承担 NRT 业务编排 |
| HMI | 操作和观察入口；展示 profile、程序、状态、日志、快照 | 不是领域 owner，不做隐藏业务状态机 |
| Tooling | 刀具、D 号、几何/磨损/可用性、preflight、HMI 投影 | 不是 tool-change executor，不做 PLC sequence |
| WorkOffset | WCS/零偏真值、当前选择、坐标上下文、HMI 投影 | 不计算最终运动矩阵，不负责页面交互 |
| Telemetry | run 证据采集、日志汇聚、report 验证 | P0 可先轻量实现，不必等待完整 diagnostics 平台 |

**架构判断**

现在最需要重排的不是“再设计更多模块”，而是把依赖方向固定下来：

1. `TP005` 不能成为入口；入口是固定基础数据包。
2. `HMI` 不能成为中枢；中枢是 `ProgramEngine session`。
3. `G-code parser` 不能直接变执行系统；它输出规范化命令，执行由 runtime/adapter 完成。
4. `Tooling`、`WorkOffset`、`TP004` 是解析和事实来源，不是运动执行者。
5. `Telemetry` 不是收尾文档工作，而是 6 道工序连续运行能否被承认的验收依赖。

最短可落地顺序应是：冻结 6 道工序输入和 profile -> 生成覆盖矩阵与基础数据包 -> 单工序端到端 -> 6 工序链 -> 8h/24h soak 与报告。
