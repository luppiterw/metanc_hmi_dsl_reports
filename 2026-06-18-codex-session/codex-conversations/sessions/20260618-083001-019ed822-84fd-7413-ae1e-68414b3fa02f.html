- High: WorkOffset real backend 启动是 all-or-nothing。默认 `preserve` 缺 store 会让 server 起不来；`replace` 又可能启动时覆盖持久数据。现在靠全局 env 控制，后面多模块会失控。
- Medium: HMI server 通过 `add_subdirectory` 拉入 `work_offset`，并强制 `WORK_OFFSET_WITH_AMENT=OFF`、`WORK_OFFSET_ENABLE_SQLITE=ON`。这适合当前桥接，但绕过了模块正常 package/ament 形态。
- Medium: C++17/C++20 边界目前压住了：HMI 公共 facade 是 C++17，真实 WorkOffset bridge 是私有 C++20。但只要 WorkOffset 头文件继续泄漏，就会扩大 blast radius。
- Medium: 当前靠 Drogon 单线程和 revision guard 维持顺序语义；未来多线程、多进程、多写者共享 SQLite 时，需要明确并发策略。
- Low/Medium: 文档/故事包还有一些旧命名会误导，例如把 `wcs.offset.table` 混在 tooling story/data dictionary 里，容易让人以为 WorkOffset 是 Tooling 子功能。

**我自己的额外观察**
- 本地 Web/QML mock runtime 在没有 `expected_revision` 时会放行 WorkOffset 写/激活路径，而真实 server 会拒绝。作为离线 demo 可以解释，但它会掩盖客户端漏带 revision 的 bug。

**后续架构讨论我建议这样分层**
1. NRT domain library + adapter：适合 WorkOffset、Tooling、参数、诊断、程序文件这类管理/投影/持久化模块。
2. NRT service/event boundary：适合多进程、多写者、需要强隔离/审计/生命周期独立的模块。
