**Findings**

1. **High: the current docs do not yet define a machine-wide authoritative owner.**
   [docs/dev/architecture.md](/home/iaar/workspace/ccmix-wp/MetaNC/docs/dev/architecture.md:281) says RT Gateway centralizes the NRT access boundary so NRT modules do not each create `rt_sdk::Machine`. But the specs only constrain gateway-owned sessions, not all processes for the same machine. [INV-003](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-02-gateway-lifecycle-ownership/SLICE-02-single-active-session-policy/INV-003.md:16) says the gateway never exposes or owns two active SDK sessions; it does not say “per machine endpoint, across all NRT deployments.” The new model’s “one authoritative owner per machine/RT endpoint” is directionally better, but it is not currently specified.

2. **High: embedded mode vs daemon/shared-owner mode is the main unresolved topology decision.**
   [STORY-02](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-02-gateway-lifecycle-ownership/STORY.md:18) explicitly allows daemon or embedded packaging, and [STORY-04](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-04-nrt-integration-envelope/STORY.md:18) defines facade plus out-of-process envelope. The new interpretation correctly surfaces this missing boundary; adopting it needs a deployment/topology rule, not just new type names.

3. **Medium: snapshot identity is too local for multi-caller or restart semantics.**
   [INV-005](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-03-runtime-state-projection/SLICE-01-state-cache-baseline/INV-005.md:16) makes revisions monotonic only “within one gateway owner lifecycle.” That is fine for the old simple model, but insufficient for the new model’s `owner_epoch/session_id/revision/stale/last_known` semantics. If clients can reconnect through facade/IPC, they need to distinguish owner restart, session replacement, stale last-known data, and new machine state.

4. **Medium: multi-machine routing is not a current committed surface.**
   [MODULE-MODEL](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/MODULE-MODEL.md:3) says the module centralizes “one active RT endpoint session.” [STORY-02](/home/iaar/workspace/ccmix-wp/MetaNC/nrt/rt_gateway/docs/spec/STORIES/STORY-02-gateway-lifecycle-ownership/STORY.md:20) repeats “one active RT session.” The new interpretation’s “multiple owners or registry mapping `machine_id -> owner`” is the right scalable shape, but it should remain a later extension unless a real multi-machine caller is in scope now.

**Old Model**

Strengths:
- Simple and aligned with current implemented slice: `GatewayCore`, `MachineClient`, `RtSdkMachineClient`, smoke harness.
- Keeps scope bounded to observability and avoids prematurely designing daemon, registry, IPC, or multi-machine infrastructure.
- Matches current architecture text: no ProgramEngine policy, no HMI state, no command forwarding, no ROS 2 surface.

Weaknesses:
- “Do not let every NRT module create `rt_sdk::Machine`” is necessary but not sufficient once there are multiple processes.
- It does not define authority outside a single module instance.
- It leaves snapshot consistency, owner restart, session replacement, and multi-server deployment as implicit behavior.

**New Model**

Strengths:
- Better architecture boundary: semantic layer, authority layer, and carrier layer separate concerns cleanly.
- Correctly prevents IPC/facade from becoming a second source of gateway semantics.
- Scales better to HMI server plus diagnostics plus scheduler callers.
- Gives a clear path for daemon/shared-owner mode and future multi-machine registry.

Weaknesses:
- Risks over-designing before the observability MVP is validated.
- Adds identity vocabulary that must be precise: `machine_id`, endpoint identity, `owner_epoch`, `session_id`, revision, stale, last-known.
- Could accidentally turn RT Gateway into a deployment manager unless “owner per machine endpoint” and “carrier only transports” are kept strict.
- Multi-machine registry should not be folded into one owner with many sessions; that would contradict the existing single-active-session invariant.

**Verdict**

Partially adopt the new model.

Adopt the boundary split now as architecture direction: semantic core, per-machine authority owner, and facade/IPC carrier. Do not implement daemon, registry, or multi-machine support yet unless a caller requires it.

Conditions before full adoption:
- Define the authority scope explicitly: “one authoritative owner per `machine_id` / RT endpoint deployment domain.”
- Define embedded legality: embedded is allowed only when the deployment has exactly one owner for that machine.
- Define shared-owner mode: multiple HMI servers/NRT processes must use facade/IPC to the same owner.
- Extend snapshot metadata with owner/session identity before relying on revisions across reconnects or clients.
- Keep multi-machine as registry-of-owners, not one owner with multiple active sessions.
