Codex Response 8 / final_answer

2026-06-24 16:57:02 +0800
只读审查结论：最大风险不是 draft 数量多，而是把“横切能力”误切成并列模块，导致 HMI、Program Engine、Scheduler、RT SDK、RT Contract 同时改同一条执行链。

**1. 最可能的耦合/重构风险**
- `rt_gateway` 容易和现有 `/rt-sdk` + SDK Communication Backend 重叠；架构已说明 backend 是 RT SDK 内部实现角色，不是 RT SDK 旁边的新架构组。若单独成模块，后续会诱导 NRT/HMI 绕过 `instruction_execution_scheduler -> rt-sdk`。
- `execution_policy` 若独立成模块，最容易和 `/nrt/instruction_execution_scheduler`、`/nrt/program_engine`、HMI mode guard、RT `machine_logic` 四处重复。当前架构明确 scheduler 负责 overlap/blocking policy，program_engine 负责执行生命周期。
- `runtime access` 名字太宽，会吞掉 RT SDK、HMI backend adapter、Data Diagnostics subscription、Program Engine execution state access。它更像访问契约层，不像一个可独立拥有业务语义的模块。
- `program execution integration` 容易变成“把 parser/kernel/scheduler/work_offset/tooling/HMI 全接一遍”的集成大包，和 Program Engine 本体重叠。
- `data diagnostics` 若按实现先行，会被 HMI runtime log store、RT process data、program progress、domain diagnostics 共用，最后变成跨层全局状态总线。
- `simulation validation` 若做成模块，会同时碰 RT GNU/Linux sim target、hardware sim、SDK contract tests、NRT dry-run、HMI fixtures；边界会很快散。

**2. 最容易交叉的职责边界**
- `Program Engine` vs `Instruction Execution Scheduler`：前者编排程序生命周期，后者调度/派发 instruction 和执行策略；不要让 Program Engine 直接承担 RT dispatch。
- `Execution Policy` vs HMI modes：HMI 只表达操作意图和模式请求，不应拥有执行互斥、等待 spindle、block/resume 的规则。
- `Runtime Access` vs `RT SDK`：RT 访问必须通过 SDK/contract，不应出现另一个“更方便”的 access facade。
- `Data Diagnostics` vs HMI retained state：诊断是发布/查询事实，不是 HMI 页面状态或缓存模型。
- `WorkOffset/Tooling` vs Program Execution：域模块拥有真值模型和合法性；Program Engine 只决定会话何时使用它们。
- `Simulation Validation` vs RT platform：仿真验证应验证同一 contract 下的行为，不应把仿真专用接口泄漏进 NRT 或 SDK 公共 API。

**3. 建议先做成接口/ADR/vertical slice 的项**
- `rt_gateway`：先做 ADR，明确它是否只是 `/rt-sdk` backend adapter 命名；不要先建模块。
- `execution_policy`：先做接口/ADR，定义 policy decision 点归属：Program Engine、Scheduler、RT machine logic 各管哪一段。
- `runtime access`：先做 contract/interface map，列出 HMI、Program Engine、Diagnostics 允许访问的 SDK surface。
- `program execution integration`：先做 vertical slice：HMI start program -> Program Engine -> Parser/Kernel/Scheduler -> RT SDK mock/contract -> Diagnostics progress。
- `data diagnostics`：先做事件/快照接口，不急着模块化；先限制数据来源、revision、订阅语义。
- `simulation validation`：先做验证矩阵/fixture slice，绑定 RT GNU/Linux sim + SDK contract tests；不要做运行时模块。

依据当前文件看，现有稳定方向是：NRT 域库 + HMI adapter 可以复用，但不能外推成 RT 通信模板。RT-facing 路径应坚持 `rt-api-contract` 先定义 wire type，`rt-sdk` 暴露用户态 API，NRT 通过 scheduler/SDK 走边界。
