我的设计是：**`parameter_id` 是不可复用的内部身份，`canonical_path` 是可读、可解析、可治理的语义地址**。两者不要合并。

**`parameter_id`**
- 用来标识“这个参数描述符本身”。
- 稳定性最高：一旦发布，不改名、不复用。
- 不应该依赖当前展示路径、Siemens 别名、owner token、存储位置。
- 用于 migration、引用关系、快照、schema diff、导入导出对账、生成代码、alias 反查。
- 可以人类可读，但语义上要当 opaque ID 用。

例子：

```yaml
parameter_id: metanc.parameter.axis.max_velocity
```

即使以后路径从：

```text
axis/{axis}/motion/max_velocity
```

调整成：

```text
motion/axis/{axis}/max_velocity
```

`parameter_id` 也不应该变。

**`canonical_path`**
- 用来表达 MetaNC 自己的语义路径。
- 面向用户、工具、HMI、搜索、导入导出和 alias 映射。
- 它不是 Siemens `$MA_...` 这种外部语法，也不是数据库 key。
- 它应该有 grammar、变量绑定和唯一性规则。
- 它可以比 `parameter_id` 更“语义化”，但变更时要通过 alias / deprecation / migration 处理。

我倾向把它分成两层理解：

```yaml
canonical_path: "axis/{axis}/motion/max_velocity"
```

这是 descriptor 级模板。

解析到具体对象实例后是：

```text
axis/x/motion/max_velocity
axis/y/motion/max_velocity
axis/z/motion/max_velocity
```

所以严格说，descriptor 里的是 `canonical_path template`，catalog / runtime lookup 里才是 resolved canonical path。字段名是否拆成 `canonical_path_template` 可以后面定，但概念上我认为必须区分。

**两者关系**
```text
parameter_id
  = 稳定身份
  = 这个参数定义是谁

canonical_path
  = 语义地址
  = 用户和工具怎么找到它

native alias / Siemens view
  = 外部兼容表达
  = 例如 $MA_MAX_AX_VELO[AX1]
```

例子：

```yaml
parameter_descriptor:
  parameter_id: metanc.parameter.axis.max_velocity
  canonical_path: "axis/{axis}/motion/max_velocity"
  owner: motion.axis
  scope: axis
```

然后 alias/view 可以映射进来：

```text
$MA_MAX_AX_VELO[AX1]
  -> canonical_path: axis/x/motion/max_velocity
  -> parameter_id: metanc.parameter.axis.max_velocity
```

我的判断：**`parameter_id` 不应该包含具体 axis/tool/channel 实例；实例身份应该是 `parameter_id + scope binding`。** 否则每个轴都要一个独立 descriptor，后续 catalog 会膨胀，也会把“参数定义”和“参数实例”混在一起。
