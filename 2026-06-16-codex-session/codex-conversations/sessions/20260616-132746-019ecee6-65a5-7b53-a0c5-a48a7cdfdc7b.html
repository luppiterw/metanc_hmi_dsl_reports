我先默认你说的是 **opencode.ai 的 OpenCode**，也就是开源 AI coding agent。

我对它的定位会很直接：OpenCode 更像一个“可自建、可换模型、可脚本化”的终端 Agent。官方现在说它支持终端、桌面 App、IDE 扩展；可以接 Claude、GPT、Gemini、本地模型等 75+ provider，也支持 GitHub Copilot、ChatGPT Plus/Pro 登录这类账号入口。它的优势不是单点补全，而是让 Agent 在 repo 里读代码、改代码、跑命令、走会话。

**我建议的使用方式**

1. **先用它做 repo 级问答**
   ```bash
   cd /path/to/project
   opencode
   /init
   ```
   `/init` 会让它分析项目并生成 `AGENTS.md`。这个文件建议进 Git，因为它会变成项目级 Agent 说明书。

2. **复杂任务先 Plan，再 Build**
   OpenCode 有 Plan mode，按 `Tab` 切换。复杂功能、跨模块改动、重构、发布流程，先让它产出计划，审一遍再让它改。小改动可以直接 Build。

3. **权限收紧**
   不建议一上来全自动。项目 `opencode.json` 可以类似这样：
   ```jsonc
   {
     "$schema": "https://opencode.ai/config.json",
     "permission": {
       "*": "ask",
       "bash": {
         "*": "ask",
         "git status": "allow",
         "git diff*": "allow",
         "npm test*": "allow",
         "rm *": "deny"
       }
     }
   }
   ```
   这样既能跑常规检查，又避免危险命令被自动执行。

4. **把它当可脚本化 Agent**
   除了 TUI，还有：
   ```bash
   opencode run "Explain this repo structure"
   opencode run --dir /path/to/project "Find likely test gaps"
   opencode serve
   opencode web
   opencode stats
   opencode export --sanitize
   ```
   适合做一次性分析、CI 辅助、批处理检查。

5. **模型选择要按任务拆**
   - 日常问答/小修：便宜快模型。
   - 深重构/架构判断：强推理模型。
   - 代码隐私敏感：本地模型或企业网关。
   - 新手：可以先用 OpenCode Zen，它是官方推荐的一组已验证模型。

**我会特别注意的坑**

- MCP 别乱开。官方也提醒 MCP server 会吃上下文，GitHub 这类很容易把 context 撑爆。
- `AGENTS.md` 要写得短而硬：构建命令、测试命令、目录边界、禁止事项、提交规范，比长篇愿景有用。
- 不要让它直接碰发布、删除、大规模格式化、迁移脚本，除非权限和工作树隔离都做好。
- OpenCode 的价值在“可控地执行”，不是“放手让它猜”。提示词里要给文件、边界、验证命令、失败时停止条件。

对，**不一样**。OpenCode 不是把你在终端里输入的文本原样发给 Claude/GPT；它有自己的 **agent runtime / wrapper / provider adapter**。

可以这样理解：

```text
你的输入
  -> OpenCode 会话层
  -> 读 AGENTS.md / config / agent prompt / 历史上下文 / 文件引用
  -> 加上工具定义 read/edit/bash/grep/apply_patch 等
  -> 通过 provider adapter 发给 Anthropic/OpenAI/Gemini/本地模型
  -> 模型返回工具调用或回答
  -> OpenCode 执行工具、做权限判断、把结果再喂回模型
```

所以“Claude 跑在 OpenCode 里”不等于 “Claude Code”。“GPT 跑在 OpenCode 里”也不等于 “Codex CLI”。底层模型可能相同，但外层的系统提示、工具 schema、上下文压缩、权限、文件读取方式、会话管理都不同，结果会明显不同。

OpenCode 自己的包装比较明显：

- 它启动时是 **TUI + 本地 server** 架构，TUI 只是 client，server 管 session/message/tool/API。
- 它有 **Build / Plan / subagent** 这些自己的 agent 概念。
- 它会把 `AGENTS.md` 项目规则放进模型上下文。
- 它有自己的工具层：`read`、`edit`、`write`、`bash`、`grep`、`glob`、`apply_patch`、MCP、自定义工具等。
- 它有自己的权限系统：`allow` / `ask` / `deny`。
- 长会话还有自动 summary / compaction agent。

Codex CLI、Claude Code 也都有自己的包装处理，只是实现不同。真正的区别不是“有没有包装”，而是 **谁负责组织上下文、谁定义工具、谁控制权限、谁执行命令、谁保存/压缩会话**。

如果你要判断某个行为是不是 OpenCode 的锅，优先看：

```bash
opencode export --sanitize
opencode debug config
opencode run --format json "..."
```

这些比直接按 Claude/GPT API 行为推断更可靠。

参考：OpenCode server 架构、session/message API、agents、tools、rules、providers 文档：

https://opencode.ai/docs/agents/
https://opencode.ai/docs/tools/

是的，可以分清楚：

**用的是 ChatGPT/OpenAI 的能力**

- 模型本身：代码理解、推理、生成、总结、重构建议。
- 模型上下文窗口：OpenCode 把文件内容、规则、历史摘要、工具结果塞进上下文。
- 工具调用能力：模型判断“我现在该读文件、改文件、跑命令还是回答用户”。
- 流式输出、推理模型特性、模型可用性和限额：这些取决于你连的是 ChatGPT Plus/Pro、OpenAI API、OpenCode Zen 还是别的 provider。
- 如果用 OpenAI provider，OpenCode 可以通过 `/connect` 选择 `ChatGPT Plus/Pro` 登录，或手动填 API key。

**不依赖 ChatGPT，而是 OpenCode 自己做的**

- TUI / Web / IDE 外壳。
- 会话管理、session、fork、undo/revert、diff。
- `Build` / `Plan` / subagent / compaction / summary 这些 agent 结构。
- `AGENTS.md`、`opencode.json`、rules、instructions 的加载和优先级。
- 工具系统：`read`、`edit`、`write`、`bash`、`grep`、`glob`、`apply_patch`、`lsp`、`webfetch`、`websearch`、MCP、自定义工具。
- 权限系统：`allow` / `ask` / `deny`。
- 真实文件读写、shell 命令执行、LSP 查询、MCP server 调用。
- 长上下文压缩、标题生成、会话摘要。
- 本地 server API：`opencode serve` 那套 session/message/tools HTTP 接口。

**不会自动继承 ChatGPT App 的这些东西**

- ChatGPT 网页版的历史对话。
- ChatGPT Memory。
- Projects、Canvas、自定义 GPTs。
- ChatGPT 的 Code Interpreter / Advanced Data Analysis 沙箱。
- ChatGPT 自带浏览器功能。
- ChatGPT 的文件库或连接器。

所以更准确的说法是：

```text
ChatGPT/OpenAI 提供“脑子”
OpenCode 提供“身体、工具、规则、权限、记忆包装和执行环境”
```

模型决定下一步想做什么，但真正读文件、改代码、跑测试、调用 MCP、压缩上下文的是 OpenCode runtime。即使用的是同一个 OpenAI 模型，OpenCode、Codex CLI、Claude Code 的行为也会不同，因为它们给模型的系统提示、工具定义、上下文组织和权限模型都不一样。

- 开源权重，适合本地部署、私有化、离线环境。
- 成本可控，不必依赖 OpenAI/Anthropic 账号。
- 可微调、量化、定制推理栈。
- 用作普通聊天、轻量代码问答、分类/抽取/局部生成时很灵活。
- 隐私边界更清楚：数据可以留在自己机器或内网。

**OpenHermes 的劣势**

- 它不是 agent 框架，不自带真实读写文件、shell、权限、diff、回滚、项目规则。
- 作为较小/老一些的开源模型系列，复杂代码推理、长上下文工程任务通常弱于当前 Claude/GPT/Gemini/Codex 级模型。
- 工具调用、结构化输出、长任务一致性要靠外层框架补。
- 部署和性能要自己负责：显存、量化、推理服务、上下文长度、吞吐。
- 对大型 repo 的导航和修改能力，单独用模型会比较吃力。

**实际建议**

如果目标是“让 AI 帮我改项目代码”，优先用：

```text
OpenCode + 强模型
```

如果目标是“本地、私有、低成本地跑一个模型”，可以用：

```text
OpenHermes + Ollama/vLLM/LM Studio
```

如果想结合两者，比较合理的是：

```text
OpenCode 作为 agent 外壳
OpenHermes 作为本地 provider
```

但要预期：OpenHermes 可以跑通流程，不一定能稳定完成复杂 repo 级任务。对于工程执行，OpenCode 的价值在“工具和流程”；OpenHermes 的价值在“可控本地模型”。

不会直接破坏代码或容器数据，但会删 **Docker 缓存/未使用镜像**，影响是“以后要重新下载或重新 build”。

```bash

```

安全，只读。只是显示 Docker 占用：镜像、容器、volume、build cache。

```bash
docker builder prune
```

删除 **build cache**。一般安全。影响：

- 下次 `docker build` 可能变慢
- 之前缓存的中间层会重新构建
- 不会删容器、volume、源码、运行中服务

比较稳的用法：

```bash
docker builder prune
```

它会询问确认。不要一开始加 `-a`，`-a` 会删更多 build cache。

```bash
docker image prune
```

默认只删 **dangling images**，也就是没有 tag、通常是旧构建残留的镜像层。一般也安全。影响：

- 可能释放一些空间
- 下次需要时重新 build/download
- 不删 volume
- 不删正在被容器使用的镜像

谨慎的是这个：

```bash
docker image prune -a
```

它会删除所有“当前没有被任何容器使用”的镜像，包括有 tag 的镜像。不会破坏数据，但你本地保留的 SDK 镜像、测试镜像、离线镜像可能没了，之后要重新拉或重新构建。

```bash

docker builder prune
docker image prune
docker system df
```

先不要用：

```bash
docker system prune -a
docker volume prune
docker builder prune -a
```

尤其是 `volume prune`，这个才容易删数据库、缓存卷、持久化数据。对于你当前这种情况，先清 build cache 和 dangling images 就够保守。

**我建议的清理顺序**

先做低风险：

```bash
docker builder prune --filter until=168h
npm cache clean --force
```

然后处理可再生缓存：

```bash
# 只在你接受下次重新下载浏览器时做
~/.cache/ms-playwright
~/.cache/puppeteer
~/.cache/hyperframes
```

最后再处理 repo 内产物和 `.git/tmp_pack_*`，这个我建议单独操作，先看每个 repo 的 `git status`，确认没有正在进行的 git 操作。

预期比较现实的释放量：

```text
保守清理：10-13G
加浏览器/npm缓存：12-16G
加 HMI generated/build：15-20G+
再压缩 WSL vhdx 后，Windows 侧 ext4.vhdx 才会真正缩小
```
